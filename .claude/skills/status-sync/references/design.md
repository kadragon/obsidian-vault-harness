# Status Sync — Design Rationale

판정은 사실상 이진 분류이고 후보는 수십 개 규모. 토큰을 세 단계로 깎는다:

1. `scan.py`가 명확한 케이스(`auto_close`/`keep_open`)를 결정적으로 분리.
2. review 후보는 scan.py가 **맥락·할 일 섹션 발췌**만 JSONL 번들로 추출 —
   메인도 서브도 원본 `.md`는 Read하지 않는다.
3. 판정은 Read만 가진 haiku 전용 `status-judge`를 **1회 배치 호출**. N번 spawn
   하지 않으므로 부팅 오버헤드가 노트 수와 무관.

폴더별 템플릿 차이(할 일/맥락/결과 헤딩)는 `scan.py`의 `PROFILES` 목록에서만
정의하고, 그 뒤 파이프라인은 폴더를 구분하지 않는다. 새 폴더가 생기면 프로파일
한 줄만 추가하면 된다.

승인 루프 중간에 메인이 본문을 재확인하지 않는다 — scan 결과와 judge TSV만으로
적용한다.

## 알려진 한계 — 구식 14_Changes 템플릿 발췌 실패 (2026-07-10 확인)

`14_Changes/incident/` 초기 노트 일부는 현재 템플릿(`## 발생 정보` / `## 할 일` /
`## 처리 결과`)이 아니라 더 오래된 변형을 쓴다:

- 컨텍스트 헤딩이 `## 발생일 / 사용자` — `context` 정규식(`수정\s*사유|발생\s*정보`)에
  안 걸림.
- 할 일·결과가 `## 처리 방안` 한 섹션에 합쳐져 있음 — `todo` 정규식(`할\s*일|Todo`)에는
  안 걸리고 `result` 정규식(`처리\s*결과|처리\s*방안|주요\s*코드`)에만 걸림.

결과: `status_excerpt`/`todo_excerpt` 둘 다 빈 문자열로 review 번들에 들어가고,
`status-judge`는 근거 없이 KEEP("발췌 부족")을 반환한다 — 이때 여러 건이 동시에 빈
발췌면 judge가 TSV 줄을 잘못된 경로에 대입하는 사고도 관찰됨(경로 중복·판정 누락).

해결하려면 `todo` 정규식에 `처리\s*방안` 별칭을 추가해야 하지만, `result` 정규식과
겹치면 같은 섹션이 todo/result 양쪽에서 이중 매치된다 — 프로파일 재설계 필요, 이번
세션에서는 미적용. 당장은: review 번들에서 `status_excerpt`와 `todo_excerpt`가 **둘 다
빈 항목**은 judge 결과를 신뢰하지 말고 원본 노트를 직접 Read해서 검증할 것.
