# Action Branch — 공문/업무요청 → `10_Areas/{area}/` 업무사안 노트

`01_Inbox/action/`의 파일·폴더를 구조화된 업무사안 노트로 변환한 뒤 원본을 정리한다.
노트는 `99_Template/_업무사안.md` 템플릿 구조를 따른다. 템플릿이 변경되면 이 절차의 노트 생성도 그에 맞춰야 하므로, 노트 작성 전 항상 `99_Template/_업무사안.md`를 Read로 확인한다.

## 처리 단위

**인라인 텍스트 입력**: 오케스트레이터가 파일 경로 없이 텍스트 내용을 직접 전달한 경우 — "1. 문서 읽기"와 "5. 노트 생성 및 파일 복사" 중 첨부파일 복사(3단계)와 "6. 정리" 삭제 단계를 건너뛴다. 이하 파일 기반 처리 단위 설명은 `01_Inbox/action/` 파일이 있을 때만 적용된다.

`01_Inbox/action/` 바로 아래 항목을 기준으로 삼는다:

- **하위 폴더** → 폴더 하나 = 업무 단위 하나. 폴더 안의 파일들은 해당 업무의 첨부 자료.
- **단독 파일** → 파일 하나 = 업무 단위 하나.
- 폴더와 단독 파일이 **혼재**해도 각각을 독립 업무 단위로 처리한다.
- 빈 폴더는 건너뛴다.

> **워커 실행 컨텍스트**: 이 문서는 `inbox-action-worker`가 읽는다. 워커는 서브에이전트이므로 **사용자와 직접 대화할 수 없고, 다른 서브에이전트를 호출할 수 없다.** 아래 절차에서 "사용자에게 확인/묻는다"로 적힌 부분은 모두 **노트의 `## 열린 질문`(또는 보고의 열린 질문 항목)으로 반환**하여 오케스트레이터가 사용자에게 전달하게 한다. 원본 삭제·vault-navigator 호출·tag-validator 호출은 워커가 하지 않는다 (오케스트레이터 담당).

처리 대상 목록과 `10_Areas/` area 폴더 목록은 **오케스트레이터가 이미 확정하여 입력으로 전달**한다 — 워커는 재스캔·재확인하지 않는다. (목록이 전달되지 않은 직접 실행 경로에서만 `ls 10_Areas/`로 보완한다.)

## 1. 문서 읽기

**인라인 텍스트 입력인 경우 이 단계 전체를 건너뛴다** — 호출 프롬프트에 내용이 이미 포함되어 있다. "2. 문서 내용 분석"부터 시작한다.

각 처리 단위에 대해 문서를 읽는다.

### 파일 형식별 처리

| 확장자 | 처리 방법 |
|--------|-----------|
| `.txt` | Read 도구로 직접 읽는다 |
| `.pdf` | 선제 헤더 검사 → 일반 PDF 또는 Handysoft 추출 (아래) |
| `.xlsx`, `.docx`, `.hwp` 등 | 내용 분석 없이 첨부파일로만 처리한다 |

### PDF 읽기 절차

1. **선제 헤더 검사**: Read 전에 Bash로 파일 헤더를 확인한다.
   ```bash
   head -c 50 "파일경로.pdf"
   ```
   - `%PDF-`로 시작하면 → 일반 PDF. Read 도구로 바로 읽는다.
   - `Handysoft`로 시작하면 → Handysoft 전자결재 파일. 아래 추출 절차를 따른다.
   - 그 외 → 알 수 없는 형식. 건너뛰고 사용자에게 알린다.

2. **대용량 PDF 대응**: Read 도구로 PDF를 읽을 때 `pages` 파라미터를 활용한다. 10페이지 초과 PDF는 먼저 `pages: "1-5"`로 앞부분만 읽어 핵심 내용(제목, 발신부서, 요청사항)을 파악한다. 필요 시 추가 페이지를 읽는다.

3. **이미지 기반(스캔) PDF**: Read가 텍스트를 거의 못 뽑으면 미파싱으로 건너뛰지 말고 OCR한다. 번들 스크립트를 직접 호출한다(매번 코드 재작성 금지):
   ```bash
   python3 .claude/skills/inbox-process/scripts/ocr_pdf.py "파일경로.pdf" --pages 1-5
   ```
   대용량은 `--pages`로 앞부분 샘플 후 필요 범위만 추가 OCR(페이지당 수 초). 표·순서가 흐트러질 수 있으니 핵심 사실 위주로 정리한다. Tesseract+kor 데이터는 이 머신에 설치됨(`TESSDATA_PREFIX` 영구 등록).

### Handysoft 전자결재 파일 추출

한국교원대학교의 전자결재 시스템(Handysoft)에서 내보낸 파일은 `.pdf` 확장자이지만 실제로는 독자 포맷이다. 내부에 PDF가 임베딩되어 있으므로 추출이 필요하다.

추출 로직은 결정론적이므로 번들 스크립트를 직접 호출한다 (매번 코드를 재작성하지 말 것):

```bash
python3 .claude/skills/inbox-process/scripts/extract_handysoft_pdf.py "원본파일.pdf"
```

스크립트는 `%PDF-` ~ `%%EOF` 구간을 잘라 `/tmp/extracted_{md5앞8자}.pdf`에 저장하고, 성공 시 stdout 첫 줄에 출력 경로를 찍는다. 파일별 해시로 경로가 달라 동시 처리 시에도 충돌하지 않는다.

추출된 PDF를 Read 도구로 읽는다. 스크립트가 exit code 1로 실패하면(임베딩 PDF 없음 등) 해당 항목을 건너뛰고 사용자에게 알린다.

## 2. 문서 내용 분석

문서 내용에서 다음을 추출한다:

- **업무 제목**: 공문 제목 또는 핵심 요청 사항 (간결하게)
- **요약**: 요청 내용, 배경, 주요 사항을 3-5줄로 정리
- **발신 부서/담당자**: 부서명과 담당자 이름 (있으면)
- **공문 번호**: `부서명-숫자(YYYY. M. D.)` 형식으로 기안일자를 반드시 함께 기록한다 (예: `총무과-7453(2026. 3. 12.)`, `장애학생지원센터-240(2026. 2. 2.)`). 부서가 매년 번호를 초기화하므로 날짜 없이는 연도가 다른 동일 번호 문서를 구분할 수 없다 — `new_work_path.py`의 자동 중복 감지는 날짜 없는 번호만으로 substring 매칭하므로(아래 "경로 + 파일명" 절 참고) 연도가 다른 동일 번호 문서도 `duplicate_candidates`로 함께 걸릴 수 있는데, 노트에 기록된 날짜가 있어야 사람이 그 후보들을 보고 실제 중복인지 다른 해 문서인지 가려낼 수 있다. 문서에 날짜가 없으면 번호만 기록하고 생략하지 말 것. 공문 번호 자체가 없으면 이 항목을 생략.
- **할 일**: 요청받은 조치 사항 (있으면)
- **기한**: 처리 기한 (있으면)
- **문서 성격 판단**:
  - **에러 로그, 스택 트레이스, ERR_INFO 포함** → 업무사안 노트 외에 `14_Changes/incident/`에도 별도 인시던트 노트가 필요할 수 있음. `## 열린 질문`에 "에러 로그 포함 — incident-analyst 추가 호출 필요?"로 반환 (워커가 직접 생성·확인하지 않음)
  - **코드 수정, 쿼리 변경, before→after 포함** → `14_Changes/improvement/`에도 별도 개선 노트가 필요할 수 있음. `## 열린 질문`에 "개선 사항 포함 — improvement-planner 추가 호출 필요?"로 반환
  - **일반 업무 요청** → 업무사안 노트만 생성

## 3. Area 자동 판단

문서 내용의 키워드로 업무 영역을 판단한다. 키워드 매핑은 힌트이며, 앞서 파악한 실제 `10_Areas/` 폴더 목록과 대조하여 최종 결정한다.

### 키워드 매핑 (실제 존재하는 area만)

| 키워드 | Area 폴더 | 태그 |
|--------|-----------|------|
| 수업, 성적, 강의평가, 강의계획, 보강, 출석 | `수업성적/` | `#업무/수업성적` |
| 수강신청, 수강, 수강정정, 장바구니 | `수강신청/` | `#업무/수강신청` |
| 교직, 교원자격, 수료증, 적인성검사 | `교직/` | `#업무/교직` |
| 졸업, 학위, 학위수여 | `졸업/` | `#업무/졸업` |
| 교원, 공채, 임용, 채용 | `전임교원공채/` | `#업무/전임교원공채` |
| 예산, 계약, 구매 | `예산관리/` | `#업무/예산관리` |
| 전자문서, 결재, 문서관리 | `구전자문서/` | `#업무/구전자문서` |
| 개발, 시스템, 서버, 보안, 네트워크, 권한, 메뉴관리, SSO | `개발공통/` | `#업무/개발공통` |

> 태그 형식 = `#업무/{10_Areas 폴더명}` 단일 접두어. `학사/`·`공통/` 등 중간 접두어는 `validate-tags.sh` hook이 거부한다 (금지 접두어). Source of truth는 항상 `10_Areas/` 폴더명.

**판단 순서:**

1. 오케스트레이터가 타깃 area를 전달했으면 그것을 사용한다.
2. (직접 실행 경로) 키워드 매핑으로 후보 area를 선정하고 실제 폴더 목록에 존재하는지 확인한다.
3. 존재하지 않거나 판단 불가하면 `기타/`로 생성하되, `## 열린 질문`에 "area 확정 필요: 후보 {목록}"으로 반환한다.

## 4. 유사 노트 탐색 및 Wiki MOC 확인

Area가 결정되면 두 가지를 병행하여 컨텍스트를 수집한다.

### 4-A. 유사 과거 노트 힌트 (오케스트레이터 제공)

유사 노트 탐색은 **오케스트레이터가 미리 `vault-navigator`로 수집**하여 입력 프롬프트로 전달한다. 워커는 서브에이전트를 호출하지 않는다 (중첩 불가).

**입력으로 받는 힌트:**

- 유사 노트 파일 경로 목록 (최대 5건)
- 각 노트에서 사용된 `#업무/`, `#부서/` 태그 패턴

**힌트 활용:**

- **태그 참고**: 힌트의 `#업무/`, `#부서/` 태그를 새 노트 `## 관련` 섹션의 **후보 태그**로 반영 (최종 검증은 오케스트레이터가 tag-validator로 수행)
- **관련 노트 링크**: 직접 관련된 과거 노트가 있으면 `## 관련` 섹션에 `[[노트명]]` 위키링크 추가
- **할 일 패턴 참고**: 유사 업무의 조치 사항을 참고하여 할 일 항목 제안

힌트가 비어 있으면 이 단계를 건너뛰고 다음 단계로 진행한다.

### 4-B. Wiki MOC 존재 확인

area 결정 후, 해당 도메인의 운영 MOC가 있는지 확인한다:

```bash
qmd search "{도메인}-운영-MOC" -n 3
```

또는 파일 직접 확인:

```bash
ls "_Wiki/topics/{도메인}-운영-MOC.md" 2>/dev/null
```

**결과 활용:**

- MOC **존재** → 다음 단계 노트 작성 시 `## 관련` 섹션에 `[[_Wiki/topics/{도메인}-운영-MOC]]` 위키링크 추가
- MOC **없음** → 생략. 링크 추가 안 함

## 5. 노트 생성 및 파일 복사

**첨부파일 유무로 레이아웃이 갈린다** (`docs/conventions.md` → `10_Areas/ Depth Rules`):

- **첨부 있음** → `10_Areas/{area}/{YYYYMM}_{요약}/` 폴더 생성, 노트(`_` 접두)와 첨부파일을 함께 넣는다.
- **첨부 없음**(인라인 텍스트 입력, 또는 복사할 원본 파일이 하나도 없는 처리 단위) → 래퍼 폴더 없이 `10_Areas/{area}/{YYYYMM}_{요약}.md` **단일 파일**로 둔다 (`_` 접두 없음). 무첨부인데 폴더로 감싸면 `check-folder-rules.py` 훅이 경고한다.

### 폴더 및 파일 구조

```
# 첨부 있음
10_Areas/{area}/{YYYYMM}_{업무제목 요약}/
├── _{YYYYMM}_{업무제목 요약}.md     ← 업무사안 노트 (파일명 앞에 _ 접두사)
├── 공문.pdf                          ← 원본 첨부파일
└── 기타첨부.xlsx                     ← 기타 첨부파일

# 첨부 없음
10_Areas/{area}/{YYYYMM}_{업무제목 요약}.md   ← 단일 파일, _ 접두 없음
```

### 처리 순서

1. **대상 폴더 확인**: `10_Areas/{area}/` 가 존재하면 사용한다. 없으면 area 루트 폴더를 생성하고 진행하되, 신규 area 생성 사실을 `## 열린 질문`에 "신규 area '{area}' 생성함 — 확인 필요"로 반환한다
2. **경로 산출**: `new_work_path.py` 호출 — 첨부가 하나도 없으면 `--flat`을 전달한다(반환 `folder`가 `null`). 첨부가 있으면 `--flat` 없이 호출(래퍼 폴더 경로 반환). 폴더 생성은 첨부가 있을 때만 한다
3. **첨부파일 복사**: 원본 파일(PDF, xlsx, docx 등)을 해당 폴더로 복사. 복사 실패 시 사용자에게 알리고 해당 파일을 건너뛴다. **첨부 없음(`--flat`)이면 이 단계 건너뜀**
4. **템플릿 확인**: `99_Template/_업무사안.md`를 Read로 읽어 현재 템플릿 구조를 확인한다
5. **노트 작성**: 템플릿 구조에 맞춰 `note` 경로에 노트를 생성한다

### 노트 작성 기준

`99_Template/_업무사안.md`의 섹션 구조를 따르되, 각 섹션을 아래와 같이 채운다:

| 템플릿 섹션 | 채우는 내용 |
|-------------|-------------|
| frontmatter | `type: work`, `status: open` (date 필드 넣지 않음) |
| `#` 제목 | `{오늘 날짜 YYYY-MM-DD} {업무 제목}` |
| `## 관련` | **후보** `#업무/...`·`#부서/...` 태그 (오케스트레이터가 tag-validator로 최종 검증), 유사 노트 위키링크 `[[노트명]]`, 도메인 MOC 위키링크 `[[_Wiki/topics/{도메인}-운영-MOC]]` (4-B에서 확인된 경우만) |
| `## 현황` | 문서 내용 요약 3-5줄 |
| `## 관련 문서` | **첨부 있을 때만 포함**: `[[첨부파일.pdf]]` 위키링크 (embed `!` 접두 붙이지 말 것). 첨부 없으면 섹션(헤딩+콜아웃) 전체를 생략 — 빈 `[[ ]]` 플레이스홀더를 남기지 않는다 |
| `## 할 일` | 추출된 조치사항. 형식: `- [ ] 내용 📅 YYYY-MM-DD ➕ YYYY-MM-DD` |
| `## 처리 결과` | 빈 항목 (`- `) |

### 경로 + 파일명 (스크립트 위임)

폴더·노트 경로 조합, 특수문자 sanitize, 동일 슬러그 중복 시 `_2/_3` 증분, **공문 번호 기반 중복 감지**는 `scripts/new_work_path.py`에 위임한다. LLM이 직접 슬러그/sanitize 로직을 작성하지 말 것. 첨부가 하나도 없으면 `--flat`을 함께 전달한다.

공문 번호가 추출된 경우 반드시 `--doc-number`를 전달한다 (첨부 없으면 `--flat` 추가). `find_duplicates()`는 문자열 단순 포함(substring) 검사라 `--doc-number`엔 **날짜 없는 `부서명-숫자`만** 넘긴다 — 날짜까지 붙이면 과거에 날짜 없이 저장된 노트나 날짜 표기가 다른 노트와 매칭되지 않아 중복 감지를 놓친다. 날짜는 노트 본문(현황 등)에 `부서명-숫자(YYYY. M. D.)` 형식으로 기록하되, CLI 인자는 별개로 취급한다:

```bash
python3 .claude/skills/inbox-process/scripts/new_work_path.py \
  수업성적 "강의평가 결과 조회 관련" --yyyymm 202604 \
  --doc-number "학사관리과-1234" --json
```

공문 번호가 없는 경우 `--doc-number` 생략:

```bash
python3 .claude/skills/inbox-process/scripts/new_work_path.py \
  수업성적 "강의평가 결과 조회 관련" --yyyymm 202604 --json
```

출력 (JSON) — 첨부 있음:

```json
{
  "folder": "/Users/.../10_Areas/수업성적/202604_강의평가 결과 조회 관련",
  "note":   "/Users/.../10_Areas/수업성적/202604_강의평가 결과 조회 관련/_202604_강의평가 결과 조회 관련.md",
  "slug":   "202604_강의평가 결과 조회 관련",
  "sanitized_title": "강의평가 결과 조회 관련",
  "duplicate_candidates": []
}
```

출력 (JSON) — 첨부 없음(`--flat`): `folder`는 `null`, `note`는 area 루트 단일 파일(`_` 접두 없음):

```json
{
  "folder": null,
  "note":   "/Users/.../10_Areas/수업성적/202604_강의평가 결과 조회 관련.md",
  "slug":   "202604_강의평가 결과 조회 관련",
  "sanitized_title": "강의평가 결과 조회 관련",
  "duplicate_candidates": []
}
```

**`duplicate_candidates`가 비어 있지 않으면 → 노트를 생성하지 않는다.** 해당 건을 열린 질문으로 오케스트레이터에 반환한다:

```
⚠️ 중복 공문 의심: {공문 번호}가 기존 노트에서 발견됨.
기존 노트: {duplicate_candidates 경로 목록}
→ 사용자 확인 필요: 기존 노트에 내용을 추가할지, 새 노트를 생성할지?
```

오케스트레이터는 이 열린 질문을 사용자에게 보고하고, 해당 인박스 파일을 삭제하지 않는다.

스크립트가 하는 일: `{YYYYMM}_{sanitized_title}` 슬러그 생성 (공백·이모지 유지, `/\:*?"<>|` 제거), 해당 area 하위 기존 폴더·단일 `.md` 스템과 NFC 정규화 비교 후 충돌 시 `_2/_3` 증분, `--flat` 시 area 루트 단일 파일 경로(`folder=null`) 반환, `--doc-number` 지정 시 `10_Areas/**/*.md` 전체에서 해당 문자열 grep. 폴더/파일은 생성하지 않고 경로만 반환한다. `--yyyymm` 생략 시 오늘 기준.

### 규칙

- `date created`, `date modified`는 frontmatter에 넣지 않는다 (Linter 플러그인이 자동 관리)
- `tags`, `systems`, `people`, `area` 필드도 frontmatter에 넣지 않는다
- 태그는 `## 관련` 섹션에 인라인으로 작성
- `#부서` 태그 형식: `#부서/{부서명}/{직급}_{이름}` (CLAUDE.md의 부서 태그 규칙 참조)
- 할 일 형식: `- [ ] 내용 📅 YYYY-MM-DD ➕ YYYY-MM-DD` (Obsidian Tasks 플러그인)
- 기한 정보가 없으면 `📅 {오늘 날짜}`로 기록 (당일 날짜 사용)
- 한국어로 작성, 기술 용어는 영어 유지

## 6. 삭제 권고 (워커는 삭제하지 않음)

**워커는 원본 파일을 직접 삭제하지 않는다.** 성공적으로 노트로 변환한 원본의 경로를 `## 삭제 권고 (action)` 목록으로 보고하고, 실제 삭제는 오케스트레이터가 일괄 처리한다 (SKILL.md 5단계).

삭제 권고에서 **제외**할 건 (목록에 넣지 않음):
- 노트 생성이 실패한 건
- 중복 의심 등 `## 열린 질문`이 남은 건
- 인라인 텍스트 입력 (삭제할 파일이 없음)

처리 결과 보고 형식:

```
## 처리 완료 (action)
- 📄 강의평가 결과 조회 관련 → 10_Areas/수업성적/202604_강의평가 결과 조회 관련/

## 삭제 권고 (action)
- /Users/.../01_Inbox/action/강의평가 결과 조회 관련.pdf
```

Handysoft 추출 시 생성한 임시 파일(`/tmp/extracted_*.pdf`)은 워커가 자신의 작업 종료 시 정리해도 되고, 오케스트레이터가 5단계에서 일괄 정리한다.

## 에러 처리

위 오류는 모두 워커가 직접 사용자에게 묻지 않고 `## 열린 질문` 또는 보고로 오케스트레이터에 반환한다.

- **PDF를 읽을 수 없는 경우**: 선제 헤더 검사 → Handysoft면 추출 시도 → 그래도 실패 시 건너뛰고 보고에 기록한다
- **동일 폴더명이 이미 존재하는 경우**: 기존 노트가 같은 업무의 후속 건일 수 있으므로 새 노트를 생성하되 폴더명에 `_2`, `_3` 접미사를 붙이고(스크립트 자동 처리), `## 열린 질문`에 "기존 노트와 병합 검토 필요: {기존 경로}"로 반환한다
- **첨부파일 복사 실패**: 해당 파일을 건너뛰고 보고에 기록한다. 노트 생성은 계속 진행한다
- **유사 노트 힌트 없음**: 유사 노트 참고를 건너뛰고 다음 단계로 진행한다
