# Action Branch — 공문/업무요청 → `10_Areas/{area}/` 업무사안 노트

`01_Inbox/action/`의 파일·폴더를 구조화된 업무사안 노트로 변환한 뒤 원본을 정리한다.
노트는 `99_Template/_업무사안.md` 템플릿 구조를 따른다. 템플릿이 변경되면 이 절차의 노트 생성도 그에 맞춰야 하므로, 노트 작성 전 항상 `99_Template/_업무사안.md`를 Read로 확인한다.

## 처리 단위

`01_Inbox/action/` 바로 아래 항목을 기준으로 삼는다:

- **하위 폴더** → 폴더 하나 = 업무 단위 하나. 폴더 안의 파일들은 해당 업무의 첨부 자료.
- **단독 파일** → 파일 하나 = 업무 단위 하나.
- 폴더와 단독 파일이 **혼재**해도 각각을 독립 업무 단위로 처리한다.
- 빈 폴더는 건너뛴다.

처리 대상 목록을 사용자에게 보여주고, 전체 처리할지 선택적으로 처리할지 확인한다. 또한 이 시점에 `ls 10_Areas/`를 실행하여 현재 존재하는 area 폴더 목록을 파악한다(4단계에서 area 매핑 시 실제 대상으로 사용).

## 1. 문서 읽기

각 처리 단위에 대해 문서를 읽는다.

### 파일 형식별 처리

| 확장자 | 처리 방법 |
|--------|-----------|
| `.txt` | Read 도구로 직접 읽는다 |
| `.pdf` | 선제 헤더 검사 → 일반 PDF 또는 Handysoft 추출 (아래) |
| `.xlsx`, `.docx`, `.hwp` 등 | 내용 분석 없이 첨부파일로만 처리한다 |

### PDF 읽기 절차

1. **선제 헤더 검사**: Read 전에 Bash로 파일 헤더를 확인한다.
   ```bash
   head -c 50 "파일경로.pdf"
   ```
   - `%PDF-`로 시작하면 → 일반 PDF. Read 도구로 바로 읽는다.
   - `Handysoft`로 시작하면 → Handysoft 전자결재 파일. 아래 추출 절차를 따른다.
   - 그 외 → 알 수 없는 형식. 건너뛰고 사용자에게 알린다.

2. **대용량 PDF 대응**: Read 도구로 PDF를 읽을 때 `pages` 파라미터를 활용한다. 10페이지 초과 PDF는 먼저 `pages: "1-5"`로 앞부분만 읽어 핵심 내용(제목, 발신부서, 요청사항)을 파악한다. 필요 시 추가 페이지를 읽는다.

### Handysoft 전자결재 파일 추출

한국교원대학교의 전자결재 시스템(Handysoft)에서 내보낸 파일은 `.pdf` 확장자이지만 실제로는 독자 포맷이다. 내부에 PDF가 임베딩되어 있으므로 추출이 필요하다.

추출 로직은 결정론적이므로 번들 스크립트를 직접 호출한다 (매번 코드를 재작성하지 말 것):

```bash
python3 .claude/skills/inbox-process/scripts/extract_handysoft_pdf.py "원본파일.pdf"
```

스크립트는 `%PDF-` ~ `%%EOF` 구간을 잘라 `/tmp/extracted_{md5앞8자}.pdf`에 저장하고, 성공 시 stdout 첫 줄에 출력 경로를 찍는다. 파일별 해시로 경로가 달라 동시 처리 시에도 충돌하지 않는다.

추출된 PDF를 Read 도구로 읽는다. 스크립트가 exit code 1로 실패하면(임베딩 PDF 없음 등) 해당 항목을 건너뛰고 사용자에게 알린다.

## 2. 문서 내용 분석

문서 내용에서 다음을 추출한다:

- **업무 제목**: 공문 제목 또는 핵심 요청 사항 (간결하게)
- **요약**: 요청 내용, 배경, 주요 사항을 3-5줄로 정리
- **발신 부서/담당자**: 부서명과 담당자 이름 (있으면)
- **할 일**: 요청받은 조치 사항 (있으면)
- **기한**: 처리 기한 (있으면)
- **문서 성격 판단**:
  - **에러 로그, 스택 트레이스, ERR_INFO 포함** → 업무사안 노트 외에 `14_Changes/incident/`에도 별도 인시던트 노트가 필요할 수 있음. 사용자에게 "이 공문에 에러 로그가 포함되어 있습니다. 인시던트 노트도 별도로 생성할까요?"라고 확인
  - **코드 수정, 쿼리 변경, before→after 포함** → `14_Changes/improvement/`에도 별도 개선 노트가 필요할 수 있음. 사용자에게 확인
  - **일반 업무 요청** → 업무사안 노트만 생성

## 3. Area 자동 판단

문서 내용의 키워드로 업무 영역을 판단한다. 키워드 매핑은 힌트이며, 앞서 파악한 실제 `10_Areas/` 폴더 목록과 대조하여 최종 결정한다.

### 키워드 매핑 (실제 존재하는 area만)

| 키워드 | Area 폴더 | 태그 |
|--------|-----------|------|
| 수업, 성적, 강의평가, 강의계획, 보강, 출석 | `수업성적/` | `#업무/학사/수업성적` |
| 수강신청, 수강, 수강정정, 장바구니 | `수강신청/` | `#업무/학사/수강신청` |
| 교직, 교원자격, 수료증, 적인성검사 | `교직/` | `#업무/학사/교직` |
| 졸업, 학위, 학위수여 | `졸업/` | `#업무/학사/졸업` |
| 교원, 공채, 임용, 채용 | `전임교원공채/` | `#업무/학사/전임교원공채` |
| 예산, 계약, 구매 | `예산관리/` | `#업무/공통/예산관리` |
| 전자문서, 결재, 문서관리 | `구전자문서/` | `#업무/공통/전자문서` |
| 개발, 시스템, 서버, 보안, 네트워크, 권한, 메뉴관리, SSO | `개발공통/` | `#업무/공통/시스템` |

**판단 순서:**

1. 키워드 매핑으로 후보 area를 선정한다.
2. 후보 area가 실제 폴더 목록에 존재하는지 확인한다.
3. 존재하지 않으면 사용자에게 묻는다.
4. 키워드로 판단이 불가하면 `기타/`를 기본 선택지로 제시하되, 전체 area 목록도 함께 보여준다.

## 4. 유사 노트 탐색 및 Wiki MOC 확인

Area가 결정되면 두 가지를 병행하여 컨텍스트를 수집한다.

### 4-A. 유사 과거 노트 탐색 (vault-navigator)

Agent 도구로 `vault-navigator` (subagent_type) 에이전트를 호출한다.

**호출 프롬프트 예시:**

```
10_Areas/{area}/ 폴더에서 "{업무 제목 핵심 키워드}"와 관련된 과거 노트를 찾아줘.
검색 키워드: {키워드1}, {키워드2}, {키워드3}
최대 5건만 찾고, 각 노트의 파일 경로와 사용된 태그(#업무/..., #부서/...)를 알려줘.
```

**기대 결과물:**

- 유사 노트 파일 경로 목록 (최대 5건)
- 각 노트에서 사용된 `#업무/`, `#부서/` 태그 패턴

**결과 활용:**

- **태그 참고**: 유사 노트에서 사용된 `#업무/`, `#부서/` 태그를 새 노트의 `## 관련` 섹션에 반영
- **관련 노트 링크**: 직접 관련된 과거 노트가 있으면 `## 관련` 섹션에 `[[노트명]]` 위키링크 추가
- **할 일 패턴 참고**: 유사 업무에서 어떤 조치 사항이 있었는지 참고하여 할 일 항목 제안

유사 노트가 없거나 vault-navigator 호출이 실패하면 이 단계를 건너뛰고 다음 단계로 진행한다.

### 4-B. Wiki MOC 존재 확인

area 결정 후, 해당 도메인의 운영 MOC가 있는지 확인한다:

```bash
qmd search "{도메인}-운영-MOC" -n 3
```

또는 파일 직접 확인:

```bash
ls "_Wiki/topics/{도메인}-운영-MOC.md" 2>/dev/null
```

**결과 활용:**

- MOC **존재** → 다음 단계 노트 작성 시 `## 관련` 섹션에 `[[_Wiki/topics/{도메인}-운영-MOC]]` 위키링크 추가
- MOC **없음** → 생략. 링크 추가 안 함

## 5. 노트 생성 및 파일 복사

각 처리 단위마다 `10_Areas/{area}/` 아래에 **폴더를 생성**하고, 그 안에 노트 파일과 첨부파일을 함께 넣는다.

### 폴더 및 파일 구조

```
10_Areas/{area}/{YYYYMM}_{업무제목 요약}/
├── _{YYYYMM}_{업무제목 요약}.md     ← 업무사안 노트 (파일명 앞에 _ 접두사)
├── 공문.pdf                          ← 원본 첨부파일
└── 기타첨부.xlsx                     ← 기타 첨부파일
```

### 처리 순서

1. **대상 폴더 확인**: `10_Areas/{area}/` 가 존재하는지 확인. 없으면 생성 여부를 사용자에게 확인
2. **하위 폴더 생성**: `10_Areas/{area}/{YYYYMM}_{업무제목 요약}/` 폴더 생성
3. **첨부파일 복사**: 원본 파일(PDF, xlsx, docx 등)을 해당 폴더로 복사. 복사 실패 시 사용자에게 알리고 해당 파일을 건너뛴다
4. **템플릿 확인**: `99_Template/_업무사안.md`를 Read로 읽어 현재 템플릿 구조를 확인한다
5. **노트 작성**: 템플릿 구조에 맞춰 노트를 생성한다

### 노트 작성 기준

`99_Template/_업무사안.md`의 섹션 구조를 따르되, 각 섹션을 아래와 같이 채운다:

| 템플릿 섹션 | 채우는 내용 |
|-------------|-------------|
| frontmatter | `type: work`, `status: open` (date 필드 넣지 않음) |
| `#` 제목 | `{오늘 날짜 YYYY-MM-DD} {업무 제목}` |
| `## 관련` | `#업무/...` 태그, `#부서/...` 태그, 유사 노트 위키링크 `[[노트명]]`, 도메인 MOC 위키링크 `[[_Wiki/topics/{도메인}-운영-MOC]]` (4-B에서 확인된 경우만) |
| `## 현황` | 문서 내용 요약 3-5줄 |
| `## 관련 문서` | `[[첨부파일.pdf]]` 위키링크 (embed `!` 접두 붙이지 말 것) |
| `## 할 일` | 추출된 조치사항. 형식: `- [ ] 내용 📅 YYYY-MM-DD ➕ YYYY-MM-DD` |
| `## 처리 결과` | 빈 항목 (`- `) |

### 경로 + 파일명 (스크립트 위임)

폴더·노트 경로 조합, 특수문자 sanitize, 동일 슬러그 중복 시 `_2/_3` 증분은 `scripts/new_work_path.py`에 위임한다. LLM이 직접 슬러그/sanitize 로직을 작성하지 말 것.

```bash
python3 .claude/skills/inbox-process/scripts/new_work_path.py \
  수업성적 "강의평가 결과 조회 관련" --yyyymm 202604 --json
```

출력 (JSON):

```json
{
  "folder": "/Users/.../10_Areas/수업성적/202604_강의평가 결과 조회 관련",
  "note":   "/Users/.../10_Areas/수업성적/202604_강의평가 결과 조회 관련/_202604_강의평가 결과 조회 관련.md",
  "slug":   "202604_강의평가 결과 조회 관련",
  "sanitized_title": "강의평가 결과 조회 관련"
}
```

스크립트가 하는 일: `{YYYYMM}_{sanitized_title}` 슬러그 생성 (공백·이모지 유지, `/\:*?"<>|` 제거), 해당 area 하위 기존 폴더와 NFC 정규화 비교 후 충돌 시 `_2/_3` 증분. 폴더/파일은 생성하지 않고 경로만 반환한다. `--yyyymm` 생략 시 오늘 기준.

### 규칙

- `date created`, `date modified`는 frontmatter에 넣지 않는다 (Linter 플러그인이 자동 관리)
- `tags`, `systems`, `people`, `area` 필드도 frontmatter에 넣지 않는다
- 태그는 `## 관련` 섹션에 인라인으로 작성
- `#부서` 태그 형식: `#부서/{부서명}/{직급}_{이름}` (CLAUDE.md의 부서 태그 규칙 참조)
- 할 일 형식: `- [ ] 내용 📅 YYYY-MM-DD ➕ YYYY-MM-DD` (Obsidian Tasks 플러그인)
- 기한 정보가 없으면 `📅` 부분 생략, `➕ {오늘 날짜}`만 기록
- 한국어로 작성, 기술 용어는 영어 유지

## 6. 정리

처리 완료된 폴더/파일을 `01_Inbox/action/`에서 **즉시 삭제**한다. 사용자 확인을 기다리지 않는다.

단, 아래 경우에는 삭제하지 않는다:
- 노트 생성이 실패한 건
- 사용자가 이번 요청에서 "파일은 남겨줘" 등 보존 의사를 명시한 경우

삭제 후 처리 결과를 보고한다:

```
## 처리 완료 (action)
- 📄 강의평가 결과 조회 관련 → 10_Areas/수업성적/202604_강의평가 결과 조회 관련/ (원본 삭제됨)
- 📄 다문화사회 전문가 수료증 → 10_Areas/교직/202604_다문화사회 전문가 수료증 시스템 개발 요청/ (원본 삭제됨)
```

Handysoft 추출 시 생성한 임시 파일(`/tmp/extracted_*.pdf`)도 정리한다:

```bash
rm -f /tmp/extracted_*.pdf
```

## 에러 처리

- **PDF를 읽을 수 없는 경우**: 선제 헤더 검사 → Handysoft면 추출 시도 → 그래도 실패 시 건너뛰고 사용자에게 알린다
- **동일 폴더명이 이미 존재하는 경우**: 기존 노트가 같은 업무의 후속 건일 수 있으므로, 사용자에게 "기존 노트에 추가할지, 새 노트를 만들지" 확인한다. 새 노트를 선택하면 폴더명에 `_2`, `_3` 등 접미사를 붙인다 (스크립트가 자동 처리)
- **첨부파일 복사 실패**: 해당 파일을 건너뛰고 사용자에게 알린다. 노트 생성은 계속 진행한다
- **vault-navigator 호출 실패**: 유사 노트 탐색을 건너뛰고 다음 단계로 진행한다
