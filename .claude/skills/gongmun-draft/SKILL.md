# 발신 문서 초안 작성

볼트 노트를 근거로 대외 발신 문서 본문을 쓰는 절차.
수신·발신·문서번호는 시스템이 자동 생성하거나 사용자가 직접 입력하므로 **제목 + 본문**만 작성한다.

## 유형 분기 — 먼저 고른다

| 유형 | 언제 | 절차 |
|------|------|------|
| **A. 개선 결과 안내 공문** | 기능 개선을 완료해 요청 부서에 알릴 때 | 아래 Step 0~ 전 과정 (이 문서의 본류) |
| **B. 회신·안내** | 받은 공문·질의·요청에 답하거나, 일정·변경을 알릴 때 | 공통 규칙만 적용 → 아래 "B 유형" 절 |

두 유형의 공통 규칙은 같다 — **제목 + 본문만**, 아래 들여쓰기 규칙, 그리고 **모든 주장은 볼트
노트나 원문 문서에서 확인된 사실로 닫는다**. 근거를 못 찾은 문장은 쓰지 말고 사용자에게 묻는다.
회신에서 지어낸 날짜·조건 하나가 대외 약속이 되기 때문이다.

**들여쓰기 규칙:** depth 한 단계 내려갈 때마다 앞 공백 2칸씩 추가.
`1.`(0칸) → `가.`(2칸) → `1)` 또는 `-` 불릿(4칸) → `가)`(6칸).
`-` 불릿도 상위 라벨(`가.` 등)의 하위이므로 2칸 더 들여쓴다.

**총장결재 표기:** `관련`에 인용하는 공문이 총장 결재(결재권자 = 총장) 문서면 공문명 뒤에
`<총장결재>`를 붙인다 — 예: `정보전산원-2765(2026. 9. 22.) "2026학년도 교수자 인공지능 활용 지원 사업 계획 수립"<총장결재>`.
결재권자를 알 수 없으면 붙이지 말고 사용자에게 묻는다.

## Step 1: 소스 노트 파악

사용자가 노트 경로를 명시한 경우 → 해당 파일 Read.
명시하지 않은 경우 → 대화 컨텍스트에서 파일 경로 추론, 없으면 물어본다.

노트에서 아래 항목을 추출한다:

| 항목 | 위치 힌트 |
|------|----------|
| 관련 공문번호 | "관련", "-XXXX호", "공식 개발 의뢰서" 텍스트 |
| 관련 공문 제목 | 공문번호 주변 큰따옴표 안 텍스트 |
| 관련 공문 날짜 | 기안일 또는 수신일 (YYYY-MM-DD → YYYY. M. D. 변환) |
| 개선 항목 | `처리 결과` 섹션 또는 완료 체크박스(`[x]`) |
| 메뉴 경로 | 메뉴코드(hl_, hc_, hr_ 등)·화면명·경로 설명 텍스트 |
| 개선일 | 운영 배포일, 마지막 `✅ YYYY-MM-DD`, 또는 `개선일` 명시 |
| 비고 | 권한 미부여, 미배포 항목, 추가 협의 필요 사항 |
| 문제/배경 | `현황`·`처리 결과` 섹션의 GAP·문제·원인 서술 (예: "~하지 않아 ~문제 있음") |
| 무변경 항목 | 요청 범위(관련 공문·현황에 언급된 메뉴) 중 "기존에 이미 구현됨"/"기존 로직으로 충족"으로 판정된 항목 |

**관련 공문이 없는 경우 (자체 개선):**
- "관련" 항목을 노트에서 찾을 수 없으면 → `1. 관련:` 항목 전체 생략.
- `2.` 문장 앞부분을 "위와 관련하여" → "통합학사시스템" 으로 시작하도록 변경:
  `2. 통합학사시스템[및 수강신청시스템]을 다음과 같이 개선하였음을 알려드립니다.`

**개선 주제 (`{개선 주제}`) 결정:**
- 노트 제목이나 frontmatter `tags`에서 최상위 메뉴 카테고리를 추출 (예: "현장실습 관련", "수강신청 관련").
- 개선 항목이 단일 메뉴 영역이면 해당 영역명 사용.
- 여러 영역에 걸쳐 있으면 `시스템 기능 개선` 으로 통일.
- 불확실하면 `[주제 확인 필요]` 플레이스홀더 사용.

## Step 2: 메뉴 경로 재구성

노트의 메뉴코드(예: `hl_3021301_u`)나 화면명으로부터 공문에 쓸 **한국어 계층 경로**를 구성한다.

- 노트에 경로가 명시되어 있으면 그대로 사용.
- 없으면 메뉴코드 앞 2자리(hl=현장실습, hc=기초자료, hr=등록 등)와 화면명으로 추론.
- 경로가 불확실하면 초안에 `[메뉴 경로 확인 필요]` 플레이스홀더를 남기고 사용자에게 알린다.

---

## Step 3: 개선 항목 그룹화

개선 항목을 **기능 영역별**로 묶어 가/나/다… 순서로 배열한다.

그룹화 기준 (우선순위):
1. 메뉴 상위 경로가 같은 것끼리 묶기
2. 성격이 같은 것끼리 묶기 (예: 수강신청 관련, 화면 관련, 기초자료 관련)
3. 단독 항목은 단독 항목으로 둔다

각 항목 서술:
- 동사형 종결: `~기능 추가`, `~처리`, `~항목 추가`
- 불필요한 기술 상세(SP명, 커밋 해시 등)는 생략

**무변경 항목 포함 규칙:**
요청 범위(관련 공문·현황에 언급된 메뉴 여러 개) 중 일부만 실제 변경되고 나머지는
"기존에 이미 구현됨"/"기존 로직으로 충족"으로 판정된 경우, 별도 가/나 항목으로
명시한다 (요청 부서가 응답 누락으로 오인하지 않도록). 서술 예:
`~기능은 기존에 구현되어 있음`, `~은 기존 방식으로 운영되므로 별도 개선 없이 충족`.

## Step 4: 공문 본문 출력

출력 전 적용 규칙:
- "및 수강신청시스템": 수강신청시스템 관련 항목이 있을 때만 "통합학사시스템 및 수강신청시스템을" 으로 변경; 없으면 "통합학사시스템을" 으로 출력.
- 문제/배경 서술: 노트에 GAP·문제·원인 서술이 있으면 "2." 문장에 배경 한 절을 넣는다.
  - 관련 공문이 있는 경우: `2. 위와 관련하여, {배경/원인 요약}이 있어, 다음과 같이 개선하였음을 알려드립니다.`
  - 관련 공문이 없는 경우 (자체 개선): `2. 통합학사시스템[및 수강신청시스템]을, {배경/원인 요약}이 있어, 다음과 같이 개선하였음을 알려드립니다.` (Step 1의 "위와 관련하여" 생략 규칙 적용)
  - 배경이 없으면 각 경우의 기존 템플릿(바로 개선하였음을 알려드립니다)을 사용한다.
- ※ 비고: 권한 미부여·미배포 항목이 있을 때만 3번 항목 앞에 추가; 없으면 줄 전체 생략.
- 개선일: 운영 배포일 기준. 불확실하면 `{날짜 확인 필요}` 표기.
- 가/나/다 항목 수: 제한 없음. 단일 항목이면 '가.' 하나만 사용.
- 다수 수신처: 공문 본문 자체는 동일하게 작성. 초안 출력 후 Step 5에서 "수신처별 별도 발신 필요" 여부를 사용자에게 알린다.

수신·발신·문서번호는 공문 시스템에서 입력하므로 **제목 + 본문(1번~끝)**을 출력한다.
제목 형식: `통합학사시스템 기능 개선 결과 안내({개선 주제})` (개선 주제 = Step 1에서 결정).

```
제목: 통합학사시스템 기능 개선 결과 안내({개선 주제})

1. 관련: {부서명}-{문서번호}({YYYY. M. D.}) "{공문 제목}"

2. 위와 관련하여, 통합학사시스템을 다음과 같이 개선하였음을 알려드립니다.

  가. {메뉴 경로1}
    - {개선 내용1}

  나. {메뉴 경로2}
    - {개선 내용2}

  ※ {비고 사항}

3. 개선일: {YYYY년 M월 D일}.  끝.
```

## Step 4.5: 문체 감사 (필수 게이트 — A·B 공통)

초안을 사용자에게 보여 주기 전에 반드시 `Skill(prod:kr-style)`을 호출해 감사를 통과시킨다.

1. 제목 + 본문을 scratchpad 파일로 저장한다.
2. kr-style 루프를 돌린다: 감사 스크립트 실행 → `[FAIL]` 교정 → 수동 체크리스트 → 재실행.
3. **exit 0이 되어야 출력한다.** 오탐(인용한 공문 제목, 메뉴 경로, 공문 관용구 `위와 관련하여` 등)은
   고치지 않고 Step 5에서 한 줄로 알린다.
4. 교정은 표현만 바꾼다 — 사실·날짜·항목 수·판단(수용/불가)은 바꾸지 않는다. 공문 종결 형식
   (`~알려드립니다`, `~함`, `끝.`)은 유지한다.

출력한 초안이 감사를 통과한 최종본이어야 한다. 감사 전 초안을 먼저 보여 주지 않는다.

## Step 5: 확인 사항 보고

초안 출력 후, 사용자가 직접 확인해야 할 항목을 간결히 목록으로 알린다:
- 메뉴 경로 플레이스홀더가 있으면 명시
- 개선일이 불확실하면 명시
- 수신처나 '끝.' 중복 등 사용자가 수정해야 할 부분
- 수신처가 2개 이상으로 보이면: "수신처별 별도 기안이 필요한지 확인 바랍니다" 추가

## B 유형 — 회신·안내

A 유형처럼 메뉴 경로·개선 항목을 재구성할 것이 없으므로 Step 2~3은 건너뛴다. 대신 **상대가 무엇을
물었는지**를 먼저 원문에서 확정하고, 그 질문에 1:1로 답하는 순서로 쓴다. 회신이 길어지는 대부분의
이유는 묻지 않은 것까지 설명해서다.

1. **원문 확정.** 받은 공문·메일·질의 원문을 Read하고, 상대의 요구를 항목으로 분해한다.
   문서번호·시행일·요구 항목 번호를 그대로 인용할 수 있게 적어 둔다.
2. **각 항목의 답을 근거와 함께 정한다.** 답은 넷 중 하나다 — 수용 / 불가 / 조건부 수용 / 확인 필요.
   **불가·조건부는 근거(규정 조문·계약 문서·시스템 제약)를 반드시 붙인다.** 근거 없는 거절은
   재질의를 부르고, 그 재질의에 답하는 비용이 처음부터 근거를 다는 비용보다 크다.
   사용자가 이미 답을 정해 준 항목은 그 판단을 바꾸지 말고 문장만 다듬는다.
3. **본문 골격.**

```
{제목 — 상대 요구를 그대로 반영. 예: "OO 사업 OO 요청에 대한 회신"}

1. 관련: {부서·업체명}-{문서번호}({YYYY. M. D.}) "{원문 제목}"
   {메일이면: {YYYY. M. D.} 귀사 메일 "{제목}"}

2. 위와 관련하여 검토 결과를 다음과 같이 회신합니다.

  가. {요구 항목 1}
    - {수용/불가/조건부} — {근거}

  나. {요구 항목 2}
    - ...

3. {필요 시 기한·후속 조치}.  끝.
```

4. **문체.** 공문은 `~합니다`체, 업무 메일은 그보다 평이하게 쓰되 판단·근거 문장은 동일하게 남긴다.
   상대가 업체면 요구 사항을 **번호로 고정**해 회신 대조가 가능하게 한다.
5. Step 4.5(문체 감사)와 Step 5(확인 사항 보고)는 B 유형에도 그대로 적용한다 — 특히 **지어낼 뻔했던 값**(기한·담당자·
   금액)이 있었다면 플레이스홀더로 남기고 사용자에게 알린다.

## Step 6: 발송 후 기록 (A·B 공통)

사용자가 "보냈어", "상신했어", "회신했어"라고 알리면 초안의 **소스 노트**에 발송 사실을 남긴다.
초안은 대화에만 있으므로 기록하지 않으면 다음 세션은 발송 여부를 알 수 없고, 회신 대기도 추적되지 않는다.
소스 노트는 사용자가 기록을 요청한 범위이므로 편집할 수 있다. 다른 노트는 건드리지 않는다.

1. **사실 확정.** 발송일(기본 오늘), 수신자·부서, 방법(공문·메일·상신), 공문번호, 최종 제목을
   사용자 발화와 대화에서 확인한다. 사용자가 초안에서 바꾼 부분(제목·안 선택 등)이 있으면 최종본 기준으로 적는다.
   공문번호·수신자를 모르면 지어내지 말고 빼거나 묻는다 — 기록된 번호는 나중에 `관련`으로 인용된다.
2. **`## 할 일`.** 발송에 해당하는 기존 항목이 있으면 `[x]`로 바꾸고 ` ✅ YYYY-MM-DD`를 붙인다.
   없으면 새 항목을 추가한다: `- [x] {수신자}에게 {문서유형} 발송 ➕ {오늘} ✅ {발송일}`.
   상대의 회신·확인이 필요하면 후속 항목을 추가한다: `- [ ] {수신자} 회신 수령 ➕ {오늘} 📅 {기한}`
   (기한은 사용자가 준 값만 쓴다. 없으면 📅를 생략한다).
3. **`## 현황`.** callout 안에 한 줄을 추가한다: `> - {발송일} {수신자}에게 {유형} 발송({공문번호}) — {요지 한 줄}`.
   회신을 받아 기록할 때도 같은 형식으로 쓴다(`… 회신 수령 — {결과}`).
4. **`## 처리 결과`.** 발송한 최종 본문을 남겨 달라고 하면 그대로 붙인다. 요청이 없으면 붙이지 않는다.
5. **status는 사용자가 "완료 처리해줘"라고 할 때만 바꾼다.** 할 일이 모두 끝나 보여도 스스로
   `status: closed`로 바꾸지 않는다 — 일괄 전환은 `status-sync` 몫이다. 남은 할 일이 없으면 보고에
   "status-sync 대상"이라고 한 줄 적는다.

보고: 바꾼 줄(할 일·현황)과 남은 미완료 할 일을 목록으로 보여 준다.
