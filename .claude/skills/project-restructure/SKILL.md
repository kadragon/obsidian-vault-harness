# Project Restructure

한 프로젝트 폴더(`12_Projects/{YYYY}/{프로젝트}/`)를 대상으로 한다. 경로는 볼트 루트 기준이다.

## 원칙

1. 할 일 체크박스는 전부 허브에 남긴다. `weekly-report-compile`는 허브의 체크박스를 수집한다.
2. 옮긴 문장은 고치지 않는다. 경로만 새 위치로 바꾸고, 당시 파일명이 다르면 `(당시 파일명 \`…\`)`을 붙인다.
3. 파일을 삭제하지 않는다. 해시가 같은 중복 파일은 목록으로 보고하고 사용자 확인을 받는다.
4. 폴더 이동은 계획 목록을 먼저 보여 주고 승인을 받은 뒤 실행한다.
5. 노트 본문에 표를 쓰지 않는다. 목록 한 줄에 `항목 — 값 — 링크` 순서로 쓴다.
6. 체크박스가 아닌 줄에 Tasks 이모지(`📅` `✅` `➕`)를 쓰지 않는다. `2026. 10. 13.까지`처럼 글로 쓴다.
7. `_Wiki/log.md`의 과거 항목은 고치지 않는다. 새 항목을 추가해 옮긴 노트의 새 링크를 적는다.
8. 프로젝트 밖 노트의 참조는 목록으로 보고하고, 승인을 받은 뒤 고친다(Golden Principle 1).

## 절차

### 1. 현황 파악

```bash
python3 .claude/skills/project-restructure/scripts/restructure.py scan "12_Projects/{YYYY}/{프로젝트}"
python3 .claude/skills/project-restructure/scripts/restructure.py verify "12_Projects/{YYYY}/{프로젝트}" --out "{scratch}/before.json"
```

- `scan` 결과: 허브 줄 수·체크박스 수, 루트 파일, 폴더별 파일 수, 해시 중복 묶음.
- `before.json`은 7단계 검증의 기준선이다. 이미 끊긴 링크도 여기에 기록된다.
- 허브와 하위 노트를 Read로 읽는다. 허브가 길어진 원인(하위 로그·대체된 결정·근거 경로)을 찾는다.

### 2. 단계 정하기

- 단계는 사업 절차 순서로 나눈다. 예: 수요조사·예산 → 사업계획 → 과업심의 → 보안성검토 → 계약 → 계정 배포 → 성과평가.
- 폴더 이름은 `{번호}. {단계명}/`, 참고 자료는 `99. 참고/`로 한다.
- 프로젝트에 이미 번호 단계 폴더가 있으면 그 번호와 이름을 그대로 쓴다.
- 기존 주제 폴더(`과업심의/`·`보고/` 등)는 해당 단계 폴더 안으로 옮기거나 이름에 번호를 붙인다.
- 공문 붙임 묶음처럼 의도적으로 중복된 파일은 그대로 둔다.

### 3. 이동 계획 승인

manifest(TSV, `from<TAB>to`, 프로젝트 폴더 기준 상대 경로)를 scratch 폴더에 쓴다. 폴더는 통째로 옮길 수 있다.

```bash
python3 .claude/skills/project-restructure/scripts/restructure.py move "{프로젝트 경로}" "{scratch}/manifest.tsv"
```

- dry-run 결과의 `errors`가 비어야 한다(원본 없음·대상 존재·대상 중복·자기 안으로 이동).
- 이동 목록, 새로 만들 단계 노트, 중복 파일 목록을 사용자에게 보여 주고 승인을 받는다.

### 4. 이동 실행

```bash
python3 .claude/skills/project-restructure/scripts/restructure.py move "{프로젝트 경로}" "{scratch}/manifest.tsv" --apply
```

- 되돌리기용 `manifest.undo.tsv`가 manifest 옆에 생긴다. 같은 명령에 undo 파일을 넣으면 원래대로 돌아간다.
- 비게 된 원본 폴더는 스크립트가 지운다.

### 5. 단계 노트 작성과 허브 축약

단계 노트는 옮길 진행 기록이 있는 단계에만 만든다.

- 경로: `{단계 폴더}/_{프로젝트 약칭} {단계명}.md`. 약칭은 기존 하위 노트의 접두어를 쓴다. 볼트 전체에서 이름이 겹치지 않아야 한다.
- frontmatter: `type: project`, `status:`는 끝난 단계 `closed`, 진행 중인 단계 `active`.
- 섹션: 요약(몇 단계인지와 결과) → 관련(허브 링크) → 진행 기록 → 의사결정(있을 때) → 관련 문서(이 폴더 파일).
- 파일명이 볼트에서 겹치는 첨부(`1. 소프트웨어 과업내용 심의요청서.hwpx` 등)는 wikilink 대신 백틱으로 적는다.

허브에서:

- 남길 것: 요약, 관련, 목표, 범위(최종 수치), 현재 진행 제약, `## 단계` 목록, `## 주요 일정` 체크박스 전부, 현재 유효한 의사결정.
- 옮길 것: 체크박스 아래의 날짜별 진행 로그, 대체된 의사결정, 근거 경로 상세.
- 옮긴 체크박스 아래에는 단계 노트 링크 한 줄만 남긴다. 계약 등 남은 일에 필요한 하위 줄은 유지한다.
- `## 단계` 목록 형식: `> 1. **{단계명}** — {상태} — [[단계 노트]]`.

### 6. 참조 갱신

```bash
python3 .claude/skills/project-restructure/scripts/restructure.py refs "{프로젝트 경로}" "{scratch}/manifest.tsv"
```

- 프로젝트 안 노트의 옛 상대 경로(`` `과업심의/…` ``, `[[참고문서/…]]`)는 새 경로로 고친다.
- 프로젝트 밖 노트의 전체 경로 참조는 원칙 7·8에 따라 처리한다.
- 파일명만 쓴 wikilink(`[[노트명]]`)는 이동 후에도 연결되므로 고치지 않는다.

### 7. 검증

```bash
python3 .claude/skills/project-restructure/scripts/restructure.py verify "{프로젝트 경로}" --baseline "{scratch}/before.json"
```

- `ok: true`여야 한다. 실패 조건: 새로 끊긴 wikilink, 허브 체크박스 수 감소, 첨부 파일 해시 손실, md 수 감소.
- 기준선에 있던 끊긴 링크는 실패로 치지 않는다. 보고에 "원래부터 끊김"으로 적는다.
- 실패하면 원인을 고치고 다시 검증한다. 원인을 모르면 undo manifest로 이동을 되돌린다.

### 8. 기록

`_Wiki/log.md`에 항목을 추가한다: 허브 줄 수 변화, 새 단계 노트 링크, 이동 건수, 옛 경로 링크의 새 위치.

## 보고 형식

- 바뀐 것: 폴더 구조, 새 단계 노트, 허브 줄 수 변화, 고친 참조
- 검증: `verify` 결과(파일 수·체크박스 수·링크)
- 확인 필요: 중복 파일 삭제 여부, 프로젝트 밖 참조 수정 여부
- 원래부터 있던 문제: 기준선의 끊긴 링크 등, 고치지 않은 이유
- 되돌리기: undo manifest 경로
