# 과업심의 요청 검토 (위원 관점)

과업심의 요청 1건을 받아 **지적사항 목록 + 판정(안) + 조치 요청표**를 만든다.
결론은 항상 원문 인용으로 뒷받침한다 — 인용할 수 없는 지적은 쓰지 않는다.

**핵심 원칙 4가지**

1. **절차가 내용에 앞선다.** 위원 구성·간소화 대상·제척부터 본다(체크리스트 축 0). 여기서 걸리면 내용 판정 자체가 무의미하다.
2. **금액과 기간은 역산한다.** 산출내역서를 읽고 끝내지 말고 `scripts/cost_check.py`로 되짚는다. 산출근거가 시장 견적뿐이면 그 자체가 최상위 지적사항이다.
3. **지적은 조문으로 닫는다.** `references/legal-basis.md`에 법·시행령·지침·별표·대학 운영지침 인용이 있다. 조문을 댈 수 있는 지적과 없는 지적은 무게가 다르다.
4. **재발을 먼저 찾는다.** `references/recurring-defects.md`의 기지(旣知) 지적이 다시 들어와 있는지가 가장 방어하기 쉬운 지적이다.
5. **문서 간 대조가 본체다.** 심의요청서 · 제안요청서 · 산출내역서 · 기본계획 · 자문결과가 서로 어긋나는 지점이 실제 결함이 있는 곳이다.
6. **발주부서가 단독 확정할 수 없는 사항은 판정하지 말고 보류로 분류한다.** (계약·회계부서 소관, 소관부처 유권해석 필요 등)

## Step 0: 대상 파악

사용자가 폴더 경로를 준 경우 그대로 쓴다. 없으면 `01_Inbox/action/` 또는
`10_Areas/과업심의/{회차폴더}/{확정요청번호}/심의자료/`에서 찾는다.

사업 유형을 먼저 판정한다 — **이후 체크리스트 범위가 갈린다.**

| 유형 | 판정 근거 | 검토 범위 |
|------|----------|----------|
| SW **개발**사업 | 기능점수(FP) 산정표·적정 사업기간 산정표 존재, 신규 개발 과업 포함 | 전체 (대가산정 + 적정기간 + 평가기준 + 법제도) |
| 물품구매·구독·임차·유지보수 | 규격서·견적서 중심, 개발 산출물 없음 | 대가산정·적정기간 제외, 정합성 + 규격 경쟁성 + 계약조건 |

이어서 **심의 유형**을 판정한다 — 절차 요건이 갈린다(`references/legal-basis.md` §5).

```
총 사업금액 ≤ 1억원  또는  상용SW·표준화 보급 시스템 구매  또는  기심의 사업의 변경없는 추가
  ├─ 예   → 간소화 심의 (위원 2인 이상, 외부위원 과반수 이상)
  └─ 아니오 → 정식 심의 (위원장 포함 5~10명, 외부위원 과반수)
```

정식 심의 대상인데 2인 체제로 운영 중이면 **내용 검토 전에 사용자에게 알린다.**

## Step 1: 번들 일괄 추출

```bash
python3 .claude/skills/gwaeop-simui/scripts/extract_bundle.py "<심의자료 폴더>" -o "<scratch>/extract"
```

- `.hwpx`/`.hwp` → prod:hwpx `text.py extract -f markdown` (표 포함)
- `.pdf` → 텍스트 레이어 추출, 0바이트면 스캔본으로 표시
- `.zip` → 풀어서 재귀 처리
- 결과: 파일별 `.txt` + `INDEX.md`(파일 목록·크기·추출 상태)

**스캔본 PDF는 여기서 잡힌다.** `INDEX.md`에 `SCANNED`로 표시되면
`python3 .claude/skills/inbox-process/scripts/ocr_pdf.py` 또는 페이지를 이미지로 렌더해 Read로 직접 읽는다.
시장조사 결과·견적서가 스캔본인 경우가 많고, **그 안에 가장 결정적인 근거가 들어 있다** — 건너뛰지 않는다.

## Step 2: 사실 카드 작성

본격 검토 전에 아래를 표로 확정한다. 이후 모든 지적이 이 표를 참조한다.

| 항목 | 확인처 |
|------|--------|
| 사업명·발주부서·담당자 | 심의요청서 |
| 사업금액(VAT 포함/제외 명시) | 심의요청서 · 산출내역서 |
| 추정가격 | 제안요청서 입찰안내 (없으면 `사업금액 ÷ 1.1` 직접 계산) |
| 계약방법·입찰방식 | 심의요청서 |
| 사업기간 (개발기간 / 전체 계약기간 분리) | 심의요청서 · 적정 사업기간 산정표 |
| 요구사항 총 건수 | 제안요청서 요구사항 총괄표 |
| 첨부·별첨 실제 목록 | 폴더 실물 vs 심의요청서 첨부목록 |

`scripts/cost_check.py sum` 으로 합계·VAT·추정가격을 기계 검증한다.

## Step 4: 대가·기간 역산

SW 개발사업이면 필수. 물품구매면 건너뛴다.

```bash
# 개발비 → 환산 기능점수 (과소산정 탐지)
python3 .claude/skills/gwaeop-simui/scripts/cost_check.py fp --amount 50000000 --vat-included

# 운영·유지관리비 → 요율제(10~15%) 대비 위치
python3 .claude/skills/gwaeop-simui/scripts/cost_check.py maint \
  --dev-amount 50000000 --maint-amount 31000000 --months 36 --vat-included

# 항목 합계·VAT·추정가격 정합
python3 .claude/skills/gwaeop-simui/scripts/cost_check.py sum \
  --total 150000000 --items 50000000,31000000,54000000,6000000,9000000,0 --vat-included

# 적정 개발기간 (지침 별표 1) — 제시 기간으로 소화 가능한 규모 상한
python3 .claude/skills/gwaeop-simui/scripts/cost_check.py period --months 3 --headcount 3

# 규모를 아는 경우 정방향 산정
python3 .claude/skills/gwaeop-simui/scripts/cost_check.py period --fp 470 --headcount 3
```

판독 기준은 `references/daega-baseline.md` § 판독. 요약하면:

- **환산 FP가 과업범위에 비해 현저히 작다** → 개발비 과소산정. 요구사항 건수와 나란히 제시한다.
- **유지관리비가 요율 상한을 넘는데 실제 서비스 수준은 감당 못 한다** → 산정방식 자체가 없다는 신호. 양방향으로 함께 쓴다.
- **제시 기간·인력의 FP 상한이 요구사항 규모에 못 미친다** → 기간 산정 불성립. 역산 FP와 나란히 제시한다.
- 역산은 **산정근거를 요구하는 도구**이지 정답 금액을 제시하는 도구가 아니다. "재산정 후 제출 바람"으로 닫는다.

## Step 5: 판정 및 산출물

`references/output-format.md`를 Read하여 형식을 맞춘다.

**판정 등급 4단계**

| 등급 | 적용 |
|------|------|
| 원안 확정 | 지적사항 없음 또는 경미한 표기 오류뿐 |
| 조건부 원안 확정 | 금액·기간·과업범위는 타당, 공고 전 문구 보완으로 해소 가능 |
| 보완 후 확정 | 산출근거·견적·규격 등 **자료 추가 제출**이 있어야 판단 가능 |
| 재심의 | 사업금액 또는 적정기간의 근거 자체가 부재·왜곡 |

**산출물 3종** — 형식·문체는 `references/output-format.md`가 규정한다.

| # | 산출물 | 용도 | 문체 |
|---|--------|------|------|
| 1 | **볼트 노트** `10_Areas/과업심의/{회차폴더}/{...}_심의의견.md` | 판단 근거 기록(1차 산출물) | 평서형 `~다` 허용 |
| 2 | **검토의견본 PDF** (요청 시) | 심의 결과·판단 전달 | 개조식 `~함 / ~바람` |
| 3 | **보완요청본 PDF** (요청 시) | 요청자에게 정정·추가제출 요구 | 개조식 `~함 / ~바람` |

**2·3을 혼동하지 않는다.** 보완요청본은 **수신자가 할 일만** 남기고 담당자(간사) 몫
— 제척 처리·위원 지명·상정 일정·심의결과서 기재 — 은 전부 뺀다. 판정 등급 대신
A(상정 전)/B(심의 시)로 시급성만 전달하고, **"확인 완료 — 추가 제출 불필요" 절을 반드시 넣는다**
(대상도 아닌 서류를 만들어 오는 것을 막는다). 상세는 `output-format.md` §2-2.

**문체는 산출물마다 다르다.** 채팅 응답 문체를 전달본에 그대로 옮기는 것이 가장 흔한 사고다.
전달본을 굽기 전 `output-format.md` §3-5 자기검수 6항을 훑는다.

PDF 제작: HTML 작성(`word-break: keep-all` 필수) → Chrome headless `--print-to-pdf`
→ **PyMuPDF로 페이지를 PNG 렌더해 Read로 레이아웃 확인.**

## 하드 스톱 — 사용자에게 확인

- **정식 심의 대상(1억원 초과 등)인데 위원 구성이 요건 미달**(5명 미만 또는 외부위원 과반수 미달) → 내용 검토 전에 알린다.
- 심의요청 결재권자와 심의위원장이 동일인인 경우 → 제척·회피 사안(대학 운영지침 §7①2호). 판정 전에 알린다.
- **조문을 인용하기 전에 현행본을 확인**한다. 지침 고시번호·시행일은 `legal-basis.md` 상단 버전 주의 참조 — 확인한 번호를 심의의견에 함께 적는다.
- 승인 체크(위원별/종합 심의결과서 기입)는 이 스킬 범위 밖 — `과업심의_프로세스.md` Step 10.
  실제 승인 확인 없이 체크하지 않는다.
- 지적사항에 특정 업체명을 노출할지 여부 → 대외 전달본이면 확인 후 익명화(`RFI 회신 업체` 등).
